# .clinerules.md — ASV Investment Tracker

System prompt / ground rules for an AI coding agent working in this repository. Read this in
full before making changes.

## 1. Tech stack and core architecture

- **Frontend**: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4. Deployed to
  **Firebase Hosting** via the Next.js frameworks integration (`firebase.json`'s
  `hosting.frameworksBackend`).
- **Backend**: Firebase **Cloud Functions v2** (`firebase-functions`), Node 20, all written in
  TypeScript under `functions/`. Every backend mutation/query the client needs goes through an
  `onCall` callable — there is no separate REST API layer.
- **Database**: Postgres on **Cloud SQL**, managed by **Firebase Data Connect**
  (`dataconnect/schema/schema.gql` is the schema source of truth; migrations flow through the
  Data Connect CLI, never hand-written `ALTER TABLE`s outside `post_migrations/`).
  - **Two separate data-access paths, used deliberately for different things**:
    1. The **generated Data Connect SDK** (`lib/dataconnect/generated/`, committed, never
       hand-edited) — used by **Server Components** for simple, non-transactional reads defined
       in `dataconnect/connector/queries.gql`.
    2. **Raw `pg` via `functions/src/lib/dataconnect-admin.ts`** (`query()` /
       `withTransaction()`) — used inside Cloud Functions for anything the generated SDK can't
       do: multi-row transactions, jsonb filtering, upserts. This is the only path with write
       access; the client SDK is read-only.
- **Auth**: Firebase Auth, custom claims (`role`, `status`, `memberId`, `siteAdminMode`) minted
  server-side. A session cookie (`__session`) bridges Auth state into Next.js Server Components
  (`lib/auth/currentMember.ts`, `lib/firebase/session.ts`); `proxy.ts` (Next.js middleware) does
  the first-line route gating before any page component runs.
- **AI**: Vertex AI (Gemini, via `@google/genai`) is the default provider; OpenRouter is a
  per-feature, site-admin-configurable alternative (`functions/src/lib/aiProviderSettings.ts`).
  Google Search grounding (Vertex) or Serper.dev raw search is likewise a per-feature toggle.
  Never hardcode a model or provider — always read the current `AiProviderSetting` row.
- **Storage/integrations**: Google Drive (pitch decks, documents) and Gmail, both via
  `googleapis`, service-account-authenticated.

## 2. Folder structure — where logic lives

```
app/                      Next.js App Router pages (Server Components by default)
  (public)/                 Logged-out marketing/landing pages
  admin/                     Admin-tier pages (role = admin or site_admin)
    settings/, costs/, portfolios/   site_admin-only ("root mode") — gated in proxy.ts too
  member/                    Member-tier pages
  api/                       Route handlers (session cookie exchange, file proxies) — NOT the
                             app's API layer; most logic is Cloud Functions, not these routes.
components/                Shared React components. "use client" only where interactivity
                            (state, effects, event handlers) actually requires it — plain
                            presentational pieces stay Server Components.
lib/                        Client- and server-shared TypeScript, imported via the `@/*` alias.
  functions/                 One file per Cloud Function group, each exporting a typed wrapper
                             around `httpsCallable(...)`. Mirrors functions/src/functions/*.ts
                             shapes EXACTLY and duplicates the types rather than importing them
                             — this boundary is deliberate (never import functions/ code into
                             the web app, or vice versa; they deploy independently).
  auth/, firebase/           Session/claims plumbing, Firebase client/admin SDK init.
  dataconnect/               Generated SDK (generated/, never hand-edit) + client.ts wrappers.
  *.tsx (e.g. portfolioView.tsx)  Larger files that mix server data-loading functions with the
                             page-section components that render them, when they're only ever
                             used together (not everything needs a strict data/UI split).
functions/
  src/
    index.ts                 The ONLY place Cloud Functions are exported/registered — every new
                             function must be added here or it never deploys.
    functions/                One file per callable, named "<domain>-<action>.ts"
                             (deals-submitPitch.ts, costs-getSummary.ts, ai-portfolioQuery.ts).
    lib/                       Shared backend logic: auth.ts (requireCaller/requireAdmin/
                             requireSiteAdmin), dataconnect-admin.ts (raw pg pool), one file per
                             external integration (vertexAi.ts, openRouter.ts, serper.ts, drive.ts,
                             gmail.ts), and domain logic (applyLedgerRecord.ts, rollups.ts, etc).
  schema/                    JSON Schema for AI-drafted ledger records (asv_master_portfolio_schema.json).
dataconnect/
  schema/schema.gql           Source of truth for the Postgres schema. post_migrations/*.sql
                             holds hand-written CHECK constraints / jsonb conversions Data
                             Connect's own migration can't express — reapplied after every
                             `dataconnect:sql:migrate`.
  connector/queries.gql, mutations.gql   Client-readable queries only (site_admin/admin-gated
                             via @auth directives) — never a write path for anything requiring
                             a transaction or validation; those are always Cloud Functions.
scripts/                    One-off Node scripts (migrations, backfills, diagnostics) run by
                            hand against the real Cloud SQL instance via the Cloud SQL connector
                            + firebase-tools' cached credentials — not part of any build/deploy.
```

## 3. Coding conventions — strict, non-negotiable

- **TypeScript strict mode everywhere.** No `any` without a specific, commented reason.
- **Comments explain WHY, never WHAT.** Every non-obvious file/function starts with a comment
  giving the reasoning, prior bug, or constraint that shaped the code — not a restatement of
  what the code visibly does. If removing a comment wouldn't confuse a future reader, don't
  write it. Do not add comments narrating "what changed" or referencing a task/issue number —
  that belongs in the commit message, not the source.
- **The `lib/functions/*.ts` ↔ `functions/src/functions/*.ts` boundary is load-bearing.** Every
  client-side callable wrapper duplicates its function's input/output types verbatim rather
  than importing them. Never blur this line by importing across the app/functions boundary.
- **Every Cloud Function starts with a caller check** — `requireCaller` (any signed-in, active
  member), `requireAdmin` (admin or site_admin), or `requireSiteAdmin` (site_admin only,
  strictly) from `functions/src/lib/auth.ts`. Never trust `role`/`memberId` from the request
  body; always re-derive from the verified Firebase Auth token's custom claims.
- **`== null` / `!= null`, never bare `=== undefined`,** when checking an "optional" field
  coming through a callable — the SDK serializes `undefined` as `null`, and treating only
  `undefined` as "not provided" is a real, previously-hit bug class here.
- **Money/valuation math is exact, done in code — never trust an AI-drafted number for
  arithmetic.** A model may draft a figure for human review, but any downstream split (e.g.
  `member_valuations` proportional to allocation) is recomputed deterministically in code,
  overwriting whatever the model produced.
- **Ledger entries are append-only.** Never `UPDATE` or `DELETE` a `LedgerEntry`/detail row in
  place outside the dedicated correction/delete flows (`deleteLedgerRecord.ts`); corrections are
  new entries.
- **Secrets are per-feature where blast-radius matters** (`openRouterSecrets.ts`: one OpenRouter
  key per AI feature, so a leaked/revoked key only affects one feature), and always
  `defineSecret(...)` + declared in that function's own `onCall` options — never read from a
  bare environment variable, never logged, never echoed back to a user/chat once stored.
- **No test suite exists** — correctness is enforced by `tsc --noEmit`, `eslint`, and a
  successful `next build` / `tsc` (functions), plus manual verification against the real
  deployed app. Treat a clean typecheck+lint+build as the minimum bar before calling anything
  done; do not invent test files or a test runner that isn't already part of the project.
- **Never hand-edit `lib/dataconnect/generated/`** — it's produced by `firebase
  dataconnect:sdk:generate` and is excluded from lint for that reason.
- **Schema changes always go through Data Connect**, never a manual `ALTER TABLE` against the
  live DB outside the documented migration flow (see §4). New tables/columns are additive and
  nullable/defaulted wherever possible so existing rows and deployed code paths never break.
- **Style**: Tailwind utility classes directly in JSX (no CSS modules, no styled-components);
  dark mode via `dark:` variants throughout; rounded-pill buttons/badges are the dominant visual
  language (`rounded-full`); server-first — a component only becomes `"use client"` when it
  actually needs state, effects, or browser APIs.

## 4. Commands

Run from the repo root unless noted. There is no automated test command — "testing" here means
typecheck + lint + build, then manual verification against the deployed app.

```bash
# --- Frontend (Next.js) ---
npm run dev              # local dev server, http://localhost:3000
npm run build            # production build — MUST pass before any deploy
npm run lint              # eslint
npx tsc --noEmit          # typecheck (no npm script defined; run directly)

# --- Backend (Cloud Functions), from functions/ ---
cd functions
npm run build             # tsc — MUST pass before any deploy
npx tsc --noEmit           # equivalent explicit typecheck
npx eslint src/...         # lint specific changed files (no repo-wide "lint" script here)

# --- Deploy (from repo root) ---
firebase deploy --only hosting                         # web app only
firebase deploy --only functions:<name1>,functions:<name2>   # specific Cloud Functions only
firebase deploy --only functions                        # all Cloud Functions
firebase deploy --only dataconnect --force               # schema/connector deploy (see below)

# --- Schema migration runbook (any dataconnect/schema/schema.gql change) ---
node scripts/drop-gin-index.js                                    # 1. drop a hand-added index Data Connect doesn't know about
firebase dataconnect:sql:migrate --force                          # 2. migrate the live Postgres schema
firebase deploy --only dataconnect --force                        # 3. deploy schema + connector
node scripts/apply-post-migrations.js \
  --instance "<project>:<region>:<instance>" --database "<db>" --iam-user "<email>"  # 4. reapply CHECK constraints/jsonb conversions
firebase dataconnect:sdk:generate                                  # 5. regenerate the committed client SDK
```

Always run the frontend's and (if touched) the functions' typecheck, lint, and build — in that
order — before deploying. Deploy functions before hosting when a change spans both, so the API
a newly-built frontend expects already exists.
